# 02 — Architecture

## System Components & Communication

Delivering `scope.inScope` (`automod_engine`, `manual_tools`, `web_dashboard`, `case_system`, `analytics`, `ticketing`, `appeals`, `multi_guild`) requires four components. `spec.json` gives no architecture detail directly — the split below is derived from which features must run *inside* the Discord gateway connection versus which are pure data/CRUD/UI concerns.

| Component | Process | Owns |
|---|---|---|
| **Discord bot** | `bot` (single long-lived process) | `automod_engine` (filter pipeline, first-pass automated action), `manual_tools` (moderator-invoked actions), all Discord-side in-message UI (buttons/selects/modals on embeds, per `integrations.notes`) and DM handling |
| **Backend API** | `api` (stateless, horizontally replicable) | `case_system`, `ticketing`, `appeals`, `analytics` aggregation, `auth` (discord_oauth session issuance), permission-builder logic, and the sole database client in the system |
| **Web frontend** | `web` (SSR/static) | `web_dashboard` — every panel in `webPortal.dashboardFeatures` (`live_log`, `analytics_charts`, `member_mgmt`, `config_editor`, `audit_viewer`, `multi_server_switch`, `case_detail`, `role_permission_ui`) |
| **Shared datastore** | managed Postgres + managed Redis | system of record (`bot` and `web` never connect to either directly) |

**Why the bot is its own process and not a module inside `api`:** `automod_engine` must evaluate every `messageCreate` event against the gateway connection's live cache with sub-second latency (raid/spam filters in particular), and `manual_tools` / in-message UI handlers must respond to Discord component interactions within Discord's interaction-token window. Coupling that to `api`'s request/response lifecycle (which may be replicated, restarted independently, or momentarily saturated by dashboard traffic) would risk missed gateway events. Splitting them also means `case_system`/`ticketing`/`appeals`/`analytics` — none of which need a persistent gateway connection — can scale and deploy independently of the bot.

**Communication paths:**

- **bot → api**: HTTP REST over an internal-only route prefix, `POST/PATCH https://api.internal/internal/v1/*` (e.g. `/internal/v1/cases`, `/internal/v1/tickets`, `/internal/v1/audit-log`), authenticated with a signed service JWT (`aud: "bot"`) distinct from user sessions. The bot never writes to Postgres itself — every case, ticket, appeal, or audit-log row is created by calling `api`, which is the schema owner.
- **api → bot** (reverse direction, needed when a moderator action originates in `web_dashboard` rather than Discord, e.g. confirming/reversing a case from `case_detail`): `api` enqueues a job onto a Redis-backed BullMQ queue named `discord-actions` (e.g. `{ type: 'timeout' | 'ban' | 'role_strip' | 'reverse_action', guildId, targetUserId, caseId }`); `bot` runs a worker consuming that queue and executes the action via `discord.js`, then reports completion back over the normal bot → api path (`POST /internal/v1/cases/:id/events`). A queue (not a direct synchronous call) is used so a bot restart or transient Discord API error doesn't fail the moderator's dashboard action — it retries automatically, which matters for the `technical.uptimeTarget: "99.9"` budget (see Deployment section).
- **api → db**: Prisma Client from `api` only, pooled through PgBouncer.
- **frontend → api**: `web` calls `GET/POST/PATCH https://api.<domain>/api/v1/*` for all CRUD (session cookie from `auth`, see Technology Stack below), and opens a Socket.IO connection to `wss://api.<domain>/realtime` for `webPortal.realtimeUpdates: true`. `web` never talks to `bot` or the datastore directly.
- **Guild scoping**: every `api` route and every socket room is namespaced by `guildId` (`guild:{guildId}`) from the start, so `multi_server_switch` and 10-multi-guild-support.md's requirement that adding a guild be a row insert, not a schema or routing change, hold structurally.

## Technology Stack Decisions

`technical.techStack` is blank in `spec.json` — the choices below are made here so an agent can scaffold the repo with no further product decisions needed. All three services share one language to keep a small team (implied by the `reduce_workload` goal) working across the whole stack without a context switch, and share type definitions for `Case`/`Ticket`/`Appeal`/`AuditLogEntry` (see 03-data-model.md) through a single npm/pnpm workspace.

| Layer | Choice | Why |
|---|---|---|
| Monorepo | pnpm workspaces: `bot/`, `api/`, `web/`, `packages/shared-types/` | one language, one lockfile, shared DTOs between `bot`'s internal-API calls, `api`'s route handlers, and `web`'s fetch layer |
| Bot | TypeScript + `discord.js` v14 | `integrations.slashCommands: false` forces every interaction onto Discord's native message-component system (buttons, select menus, modals) and DMs (`integrations.notes`) — `discord.js` has first-class `ButtonBuilder`/`StringSelectMenuBuilder`/`ModalBuilder` APIs and mature gateway-reconnection handling, which a raw REST/gateway client would have to reimplement |
| Backend API | TypeScript + Fastify | lightweight, low per-request overhead (matters for `targetServerCount: "small"` cost envelope), first-class `@fastify/websocket`/Socket.IO integration for `realtimeUpdates: true`, and typed route schemas (via `@fastify/type-provider-typebox`) that double as request/response validation for the payloads listed under System Components above |
| Realtime transport | Socket.IO (server in `api`, client in `web` and internally consumed by `bot`'s notification path) | built-in reconnection and room semantics map directly onto per-guild scoping (`guild:{guildId}` rooms for `multi_server_switch`); the Socket.IO Redis adapter lets `api` run >1 replica (needed for the uptime target below) while still broadcasting `case.created`/`case.updated`/`ticket.created`/`log.appended`/`analytics.updated` events to every connected dashboard regardless of which replica holds the socket |
| Web frontend | Next.js 14 (App Router) + Tailwind CSS | Tailwind's responsive utility classes satisfy `webPortal.mobileResponsive: true` without a separate mobile codebase (`scope.launchPlatforms` includes `mobile_web`, not a native app); Next.js App Router gives per-guild routes (`/dashboard/[guildId]/...`) and SSR for the initial `audit_viewer`/`case_detail` page loads, falling back to the Socket.IO client for live updates thereafter |
| Auth | NextAuth.js with a custom Discord OAuth2 provider, session persisted as an httpOnly cookie validated by `api` | directly implements `webPortal.authMethod: "discord_oauth"`; full scope/permission-mapping design (`admin`/`moderator`, `customPermissionBuilder`) is in 09-auth-and-permissions.md — this section only fixes the mechanism |
| Database | PostgreSQL via Prisma ORM | relational foreign keys are the natural fit for `Case → Appeal`, `Case → AuditLogEntry`, `Guild → *` relationships (see 03-data-model.md); Prisma migrations give the schema-authority guarantee that only `api` owns the DB (System Components, above) |
| Cache / queues | Redis | three independent uses: (1) sliding-window counters for `spam`/`raid`/`mass_mention` filters (`automod:{guildId}:{userId}:msgCount`, keyed with a TTL — see 04-automod-engine.md), (2) BullMQ queues (`discord-actions` for api→bot commands, a repeatable job for the 90-day retention sweep — see 11-data-privacy-compliance.md), (3) Socket.IO's Redis adapter for cross-replica broadcast |

## Deployment & Hosting Model

`technical.hostingModel: "cloud"`, `technical.targetServerCount: "small"`, and `technical.budgetNotes: ""` (blank) together mean: cloud-hosted, but sized and priced for a small deployment, not a multi-region SaaS footprint — no Kubernetes cluster, no multi-region failover, no dedicated ops team assumed.

**Platform:** a single-vendor PaaS with persistent-process support — Fly.io (or an equivalent, e.g. Railway) — rather than a serverless-functions platform. This is a direct consequence of the component split above: `bot` holds one persistent Discord gateway WebSocket connection that cannot be modeled as a short-lived serverless invocation, so whatever host runs `bot` must support long-running processes; running `api` and `web` on the same platform avoids paying for and operating a second vendor.

**Process topology (small scale ⇒ no sharding needed):**

- `bot` — **1 instance.** Discord requires gateway sharding only around ~2,500 guilds; `scope.targetServerSize: "small"` is far below that, so a single shard/single process is sufficient. This is a deliberate single point of failure for the gateway connection, accepted because of the cost envelope implied by blank `budgetNotes` — mitigated by the health-check/restart strategy below, not by running redundant bot instances (which `discord.js`/Discord's gateway would treat as duplicate sessions, not failover).
- `api` — **2 instances** behind the platform's load balancer, stateless (Socket.IO Redis adapter makes this safe — see Technology Stack). Two replicas is the cheapest way to buy real redundancy: a crash, deploy, or restart of one instance is invisible to `web` and to `bot`'s internal-API calls, which is what actually protects the 99.9% target on the highest-traffic component.
- **Postgres** — 1 managed small instance (e.g. Fly Postgres single-node, or equivalent managed offering), accessed through PgBouncer for connection pooling sized to the small `api` replica count (e.g. a 10–15 connection pool is ample at this scale).
- **Redis** — 1 managed small instance, shared by automod counters, BullMQ, and the Socket.IO adapter (all low-volume at `targetServerSize: "small"`).
- **`web`** — deployed on the same platform as a Next.js SSR service (or Vercel, if operational simplicity is preferred over single-vendor consolidation); either way it is stateless and scales the same way `api` does.

**Uptime strategy for `technical.uptimeTarget: "99.9"`** (≈43 minutes of allowed downtime per month): the target is met through fast failure recovery, not redundancy everywhere.

- `api` and `web`: rolling deploys across 2 replicas mean planned deploys cause zero visible downtime; an unplanned crash of one replica is masked by the other while the platform restarts it.
- `bot`: exposes a lightweight internal HTTP `/healthz` endpoint (a minimal Fastify listener bolted onto the same process) reporting `client.ws.status === READY`; the platform's process supervisor restarts the process on a failed check or crash. `discord.js`'s own gateway auto-reconnect handles transient network drops without a full process restart, so a process-level restart is only needed for unrecoverable failures — expected to be infrequent enough that even a single-instance bot stays inside the 43-minute monthly budget.
- `api` additionally exposes `/healthz` (process liveness) and `/readyz` (DB + Redis connectivity) so the load balancer stops routing to a replica that has lost its DB connection rather than serving 500s from it.

## End-to-End Data Flow

This traces one concrete path from an automod trigger through to a resolved appeal, tying together 04-automod-engine.md, 05-manual-moderation.md, 06-case-management-and-appeals.md, 07-ticketing-system.md, 08-web-dashboard.md, and 11-data-privacy-compliance.md at the systems level defined above.

1. A message is posted in a guild channel. `bot`'s `messageCreate` handler calls `AutomodEngine.evaluate(message)` in `bot/src/automod/engine.ts`.
2. The engine runs the filter pipeline (`bot/src/automod/filters/{spam,raid,links,profanity,nsfwImage,phishing,massMention,capsEmoji}.ts`), each implementing a common `Filter.evaluate(ctx): FilterResult | null`. Stateless filters (`links`, `profanity`, `caps_emoji`) run against the message content directly; stateful ones (`spam`, `raid`, `mass_mention`) read/increment Redis sliding-window counters. Precedence/severity ordering across filters is defined in 04-automod-engine.md; this file only fixes where the pipeline runs (in-process in `bot`, not a round-trip to `api`) so action latency isn't gated on network I/O.
3. On a violation, `bot` executes the configured first-pass action immediately via `bot/src/moderation/actions.ts` — the same `ModerationActions` module used by `manual_tools` for moderator-invoked `kick`/`softban`/`ban`/`timeout`/`warn`/`purge`/`role_strip`/`lockdown` (05-manual-moderation.md), so automated and manual actions share one execution path and one audit shape.
4. `bot` calls `POST /internal/v1/cases` on `api` with `{ guildId, targetUserId, source: "automod", filterId, actionTaken, evidence: { messageContent, attachmentUrls }, moderatorId: null }`.
5. `api`'s `CasesService.createCase()` (`api/src/modules/cases/cases.service.ts`) writes a `Case` row and an `AuditLogEntry` row (schemas in 03-data-model.md) in one Prisma transaction, then emits `case.created` on the `guild:{guildId}` Socket.IO room and updates that guild's running analytics counters.
6. Any moderator with the dashboard's `live_log` panel open (`web/src/app/dashboard/[guildId]/live-log/page.tsx`) receives `case.created` over its open socket and prepends the entry with no reload; the `analytics_charts` panel increments its totals from the same event, and reloads full ranges from `GET /api/v1/guilds/:guildId/analytics` on mount (08-web-dashboard.md).
7. A moderator opens `case_detail` (`GET /api/v1/guilds/:guildId/cases/:caseId`), reviews the evidence, and either confirms or overturns the automod verdict via `PATCH /api/v1/guilds/:guildId/cases/:caseId` with `{ status: "confirmed" | "overturned", resolutionNotes }` (06-case-management-and-appeals.md).
8. If the affected member disputes the action, an appeal enters through one of two ingress paths that converge on the same `api` call: (a) the member clicks "Appeal" on the DM `bot` sent at action time (`bot/src/dm/appealFlow.ts`, a `ModalBuilder` collecting a reason), which `bot` forwards as `POST /internal/v1/cases/:caseId/appeals { reason }`; (b) the equivalent portal-side submission path defined in 06-case-management-and-appeals.md posts to the public `POST /api/v1/guilds/:guildId/cases/:caseId/appeals`. Both call the same `AppealsService.fileAppeal()`.
9. `fileAppeal()` creates an `Appeal` row linked to the `Case`, sets the case's status to `appealed`, and emits `case.updated` (updating `live_log`/`case_detail` live) plus a `log.appended` event that feeds a pending-appeals queue view (`GET /api/v1/guilds/:guildId/appeals?status=pending`).
10. A moderator resolves it from `case_detail`'s appeals section via `PATCH /api/v1/guilds/:guildId/appeals/:appealId { decision: "upheld" | "reversed", notes }`. On `reversed`, `api` enqueues a `reverse_action` job onto the `discord-actions` BullMQ queue; `bot`'s worker consumes it, undoes the original action (e.g. clears a timeout, restores a stripped role) via `ModerationActions`, and reports completion with `POST /internal/v1/cases/:caseId/events { type: "action_reversed" }`. `api` marks the case `resolved` and pushes the final state over the socket, so `live_log`, `case_detail`, and `analytics_charts` all reflect resolution without a client refresh.

`ticketing` (07-ticketing-system.md) reuses this exact backbone rather than a bespoke pipeline: a member-initiated ticket enters through the same DM/in-message-UI pattern (`bot/src/dm/ticketFlow.ts` → `POST /internal/v1/tickets`), is pushed as a `ticket.created` event on the same `guild:{guildId}` room into a dashboard queue view structurally identical to `live_log`, and — when resolving it requires a Discord-side effect (e.g. granting a role) — closes the loop through the same `api → discord-actions queue → bot` path used for appeal reversal in step 10. `automod_engine`, `manual_tools`, `case_system`, `appeals`, and `ticketing` therefore all share one architectural shape: bot ingress → internal API write → Socket.IO push → dashboard render → optional queued command back to the bot.

Every `Case`, `Appeal`, `Ticket`, and `AuditLogEntry` row created along this path is subject to the 90-day sweep (`dataAndPrivacy.dataRetentionDays: "90"`) specified in full in 11-data-privacy-compliance.md, implemented as a BullMQ repeatable job (`api/src/jobs/retentionSweep.ts`) — a single scheduled query rather than a partitioned pipeline, consistent with the "small"-scale data volume established in 01-overview.md.
