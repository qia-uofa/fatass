- Already in use for a conda environment at `/scratch/qi/env` (standard

- **Anything large** — datasets, model weights/checkpoints, conda/pip
  environments, build caches, intermediate experiment outputs — belongs
  here, not under the home-dir project tree.
- **Not persistent**: nothing here is guaranteed to survive — no backups,
  and scratch storage on clusters like this is routinely wiped or purged.
  Anything placed under `/scratch/qi` must be **easily reproducible from
  what's stored in `~`** — e.g. an `environment.yml`/`requirements.txt`
  checked into the home-dir project plus a documented `conda create`/`pip
  install` step to rebuild `/scratch/qi/env`, or a script/command
  (tracked in the repo) that regenerates a dataset or checkpoint rather
  than treating the scratch copy itself as the source of truth. Never
  store anything under `/scratch/qi` that can't be regenerated this way.

## Where reproduction code lives in the topology

Per project convention, the actual code generated to reproduce the
paper's experiments is stored under the `reproduction` node itself
(`thesis.reproduction`, topology dir
`fatass/topology/thesis/reproduction/`, mirrored assets under
`home/thesis/reproduction/`) — not scattered across `info`/`experiment`
sibling nodes, which hold planning/spec/inspection documents rather than
the reproduction implementation itself. Given the home-dir quota
constraint above, large runtime artifacts that this generated code
produces (datasets, checkpoints, logs) should be redirected to
`/scratch/qi` even though the code and small tracked outputs stay under
the home-dir topology/asset tree.
